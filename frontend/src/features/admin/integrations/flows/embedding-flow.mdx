# 임베딩 flow

연동된 도구의 데이터를 CatchUp에 넣는 과정이다. [커넥터 연결 flow](?path=/docs/flows-커넥터-연결--docs)가
다루는 연결(크리덴셜 검증)과는 **별개의 상태 기계**다 — 연결 상태는 (채널톡 기준) idle → tested → error로 움직이고,
임베딩은 작업(job) 단위로 pending → in_progress → success/failed로 움직이며, 임베딩의 성공·실패는
연결 상태에 아무 영향도 주지 않는다.

진입 경로는 도구에 따라 둘로 갈린다:

- **채널톡** — 연결 2스텝의 스텝 ②에서 채널·도큐먼트 스페이스를 계층으로 고른다. 채널 수만큼 요청이 병렬로 나간다.
- **다른 커넥터**(Slack·Github·Jira·Confluence) — 연결됨 상세의 [임베딩 추가]가 여는 모달에서 고른다. 요청은 1개다.

라이프사이클은 다섯 단계다: **대상·기간 선택 → 제출 → 진행 → 성공/실패 이력 → 재시도**.
마지막 장은 "있을 것 같지만 없는 것들"이다 — 문서를 읽고 없는 기능을 찾지 않도록.

## 1. 대상·기간 선택

**채널톡** — 스텝 ②의 계층 선택기. 채널과 도큐먼트 스페이스 각각에 기간을 붙일 수 있고, 기본 기간은 '전체'다.

<Canvas of={TargetPickerStories.Default} />

**다른 커넥터** — 임베딩 모달. 기간과 대상을 고른다. 채널톡과 달리 **기본 기간이 '3년'이고 '전체' 옵션 자체가 없다**
— '전체'는 채널톡 선택기 전용 개념이다. 알아둘 규칙 하나: 우측 상단 "전체 선택하기"는 검색으로 목록을
좁힌 상태에서도 **검색 결과가 아니라 접근 가능한 전체**를 선택한다.

<Canvas of={EmbeddingModalStories.Default} />

### 주요 분기

**아직 임베딩된 것이 없을 때** — 연결됨 상세의 관리 탭이 빈 상태 안내를 보여준다.

<Canvas of={EmbeddingEmptyStories.Default} />

## 2. 제출

하단 바(채널톡) 또는 모달 푸터(다른 커넥터)의 [임베딩하기]가 트리거다. 선택 0개면 비활성.

<Canvas of={FooterStories.SomeSelected} />

제출 시점에 화면에 보이지 않는 규칙들이 작동한다:

- **기간 계산(sync_days)** — 백엔드는 요청당 기간 하나만 받는다. 그래서 채널 안에서 채널 기간과
  스페이스 기간들 중 **가장 긴 것**이 채택되고, '전체'가 하나라도 섞이면 기간 없음(전체)으로 보낸다.
  이 계산은 **채널마다 독립**이다 — 한 채널의 '전체'가 다른 채널로 전염되지 않는다.
  스페이스에 기간을 따로 정하지 않으면 채널 기간을 상속받는 게 아니라 독립적으로 '전체'로 처리된다.
- **부분 실패 시 알림은 성공이 우선이다** — 채널톡은 채널 수만큼 병렬 요청이 나가는데, 하나라도 시작되면
  성공 토스트("N/M개 채널…")만 뜨고 **실패한 채널의 사유는 알림에 나오지 않는다**. 전부 실패했을 때만
  이미 진행 중(conflict) → 데이터 없음(no_events, 전 채널이 해당할 때만) → 실패 순서로 원인 토스트가 뜬다.
- **화면 전환 규칙** — 시작됨(accepted)이거나 이미 진행 중(conflict)일 때만 스텝 ②를 벗어나
  연결됨 상세로 돌아간다. 전부 실패이거나 데이터가 없으면 **스텝 ②에 그대로 머문다**.
- 이미 진행 중(conflict)이어도 그 작업을 추적 대상에 편입시켜 진행 중 표에 띄운다.

## 3. 진행 중

연결됨 상세의 **임베딩 현황** 탭. 진행 중인 작업이 있으면 표로 나오고, 탭에 점이 붙는다.

<Canvas of={ActiveTableStories.Running} />

<Canvas of={SegmentTabsStories.RunningDot} />

화면 뒤의 규칙:

- 진행 상태는 **10초 간격 폴링**으로 갱신되고, 성공/실패에 도달하면 폴링이 자동 중단된다.
- 추적 중인 작업은 브라우저 저장소(sessionStorage)에 남아 **새로고침해도 이어진다**. 화면에
  다시 들어오면 서버의 활성 작업을 한 번 조회해 복원한다.
- 진행 중 표에는 **아직 끝나지 않은 대상만** 남는다 — 완료된 대상은 이력으로 넘어가고,
  같은 대상이 여러 작업에 걸쳐 있으면 하나로 합쳐 보여준다.
- 탭의 점은 별도 API 신호가 아니라 "진행 중 표에 뭔가 있는가"의 파생값이다.

## 4. 성공/실패 이력

임베딩 현황 탭의 히스토리. 전체/성공/실패 필터 칩은 항상 하나가 선택되어 있다(전체 해제 불가).

<Canvas of={HistoryTableStories.FilterChips} />

**실패 행** — 실패 건수와 함께 [재시도] 버튼이 붙는다. 재시도 버튼은 실패 행에만 있다.

<Canvas of={HistoryRowStories.Failed} />

**실패 건수 상한 표기** — 실패가 50,000건을 넘으면 "50,000+건"으로 표시한다. 정확히 50,000건이면
+를 붙이지 않는다. 이 상한 규칙은 실패 건수 배지 전용이다.

<Canvas of={HistoryRowStories.FailedOverCap} />

화면 뒤의 규칙: 이력에는 **완료된 것만** 나온다 — 진행 중·대기·재시도 중인 대상은 이력에서
명시적으로 제외된다(진행 중 표가 담당). 필터 칩의 건수 배지와 실패 빨간 점은 디자인 미결(#18)로 보류 중이다.

## 5. 재시도

이력의 실패 행에서 [재시도]를 누르면 확인 모달이 뜬다. 재시도의 정체를 정확히 알아두자:

- **전체 재임베딩이 아니다.** 실패한 레코드(gap)만 골라 부분 재처리를 요청한다. 새 작업(job)이
  생기지 않으므로 **진행 중 표에는 절대 나타나지 않는다.**
- 재시도 중 유일한 피드백은 **모달의 블로킹 화면**이다("다시 임베딩을 진행하고 있어요…").
  이때 모달은 닫을 수 없고, 완료되면 저절로 닫힌다.
- 이력 표 어디에도 "재시도 중" 표시는 없다 — 이력은 재시도 중인 대상을 숨기고, 행 상태에
  재시도 중이라는 값 자체가 없다.

**4회 이하** — "실패한 N개만 다시 해볼까요?" 제안. 빠르게 끝난다는 안내.

<Canvas of={RetryModalStories.FirstRetry} />

**5회 이상** — 재시도 카운트 카드가 나타나고, 카피가 "완료되지 못했어요"로 바뀌며 문의를 유도한다.

<Canvas of={RetryModalStories.Exhausted} />

**재시도 진행 중** — 닫기 버튼 없는 블로킹 화면.

<Canvas of={RetryModalStories.Loading} />

## 6. 있을 것 같지만 없는 것들

- **임베딩된 리소스의 삭제·해제** — 없다. 임베딩된 채널/스페이스 표에는 행 액션이 없다.
  채널톡 연결 화면의 채널/스페이스 삭제는 크리덴셜 등록을 지우는 것으로, 임베딩된 데이터 삭제가 아니다.
- **부분 실패의 사유 노출(채널톡)** — 없다. 일부만 실패하면 성공 토스트에 묻힌다 (§2).
- **재시도 중 표시** — 없다. 모달 로딩 화면이 전부다 (§5).
- **전체 선택의 부분 선택(indeterminate) 표시** — 없다. 전부 선택했을 때만 체크된다(사용자 결정).

채널톡 2스텝 패널의 자체 로딩/에러 화면(패널 진입, 스텝 ② 대상 로딩)은 스토리가 없어 이 문서에
임베드하지 못했다 — 훅이 배선된 컴포넌트라 스토리화에 별도 작업이 필요하다.
